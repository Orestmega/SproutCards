# Проєкт: застосунок із картками для вивчення мов (PWA)

Постійні інструкції для Claude Code. План: `PLAN.md`. Журнал і стан: `JOURNAL.md`.

## Що будуємо

Повноцінний продукт для пет-проєкту й резюме та для власного користування: застосунок із
картками для вивчення будь-якої мови. Це **сайт, який встановлюється на телефон як додаток (PWA)**.
Магазини (App Store, Google Play) не плануються; з 2026-10-29 за рішенням власника додатково є обгортка Capacitor для Android і iPhone (`android/`, `ios/`, `docs/NATIVE_APPS.md`), без публікації в магазинах. Одна кодова база, працює офлайн, дані зберігаються
на пристрої. Акаунти й хмарна синхронізація не входять у першу версію.

Узгоджена специфікація:
- Стек: TypeScript, React, Vite, PWA (service worker, manifest), IndexedDB (бібліотека Dexie),
  Vitest + Testing Library для тестів. Python не використовуємо.
- Мови навчання: перша пара англійська ↔ українська, але модель даних і код не прив'язані до мов: будь-яка
  пара мов задається кодами (BCP 47: `en`, `uk`, `de` тощо).
- Мова інтерфейсу: українська й англійська (файли перекладів, перемикач).
- Режими навчання: картки з перевертанням; Learn (вибір відповіді, потім введення, помилки повертаються
  в чергу, потім зворотний напрямок); тест; озвучка слів (Web Speech API, `speechSynthesis`).
- Картки: відкриті дані (частотні слова, переклади, приклади речень) плюс власні колоди користувача.
  Імпорт та експорт колод файлом (JSON; CSV за можливості) як резервна копія.
- Дизайн: світла тема; оригінальний талісман «Sprout» у SVG (простий, зелений, зі «сторінкою» на голові);
  великі закруглені картки-варіанти там, де вибір; компактні списки колод; темна кнопка з об'ємним нижнім
  краєм; прогрес-смуга зверху на екранах навчання. Палітра і правила в `docs/DESIGN.md`.
  Не копіюй інтерфейс, брендинг чи персонажів Quizlet, Duolingo, Brilliant та інших.

## Правила автономної роботи

Власник хоче, щоб усе було зроблено без його втручання. Тому:

1. **Не став питань під час роботи.** Коли потрібне рішення, візьми розумне, запиши в `JOURNAL.md` у
   «Рішення» (дата, що вирішено, чому, яка альтернатива) і продовжуй.
2. **Єдині винятки: рішення власника.** Список у `JOURNAL.md`, розділ «Черга рішень власника» (хостинг,
   push на GitHub, остаточна назва, юридичні питання щодо даних). Для них роби підготовку, запиши
   рекомендацію й варіант за замовчуванням, а саму дію не виконуй, поки власник не підтвердить у чаті.
3. **Працюй за частинами з `PLAN.md`.** Виконай рівно ту частину (кілька етапів підряд), про яку просить
   власник, потім зупинись. Власник дасть окремий запит на наступну. Так контролюються ліміти. Після кожного
   етапу всередині частини: повні перевірки, коміт, оновлення `JOURNAL.md`. Якщо ліміт закінчується,
   зупиняйся на межі етапу й запиши, звідки продовжувати.
4. **Контроль витрат.** Одну проблему не штурмуй більше 3 спроб: запиши в «Відомі проблеми» і йди далі
   (якщо вона не блокує етап). Не запускай нескінченних циклів, довгих збірок і тестів без таймауту.
5. **Стан у файлах, не в пам'яті.** Наприкінці етапу онови `JOURNAL.md` (блок «Поточний стан»: що зроблено,
   що перевірено з командою і результатом, що ні, що далі). Новий етап починається з читання цих файлів.
6. **Чесність.** Не пиши, що щось працює, якщо ти цього не запускав. Поведінку на iPhone, Safari і в
   реальному офлайн-режимі на пристрої без перевірки позначай «не перевірено на пристрої». Не вигадуй
   результатів Lighthouse чи тестів.
7. **Самоперевірка.** Наприкінці етапу перечитай власні зміни, запусти повний набір перевірок (див. нижче)
   і виправ знайдене. Окремо шукай: відсутні обробки помилок, хардкод рядків інтерфейсу, втрату даних
   користувача.
8. **Власник вивчатиме код пізніше.** Тому пиши зрозумілий код, короткі коментарі там, де логіка не
   очевидна, і підтримуй `docs/ARCHITECTURE.md` та `docs/HOW_IT_WORKS.md` (українською, простими словами).
   Питань на розуміння не став, власник про них не просив.

## Технічні правила

- Мова коду, коментарів, комітів, README: англійська. Рядки інтерфейсу тільки через файли перекладів
  (`uk`, `en`), без хардкоду. Документи для власника (`docs/HOW_IT_WORKS.md`, `JOURNAL.md`): українська.
- Логіка (планувальник повторень, рушій Learn, нормалізація відповідей) у чистих функціях без залежності
  від React та браузера, з тестами. Тести спершу для неї.
- Сховище: IndexedDB через Dexie. Міграції схеми версіонувати. Дані користувача не можна втрачати при
  оновленні застосунку.
- Strict-режим TypeScript, ESLint, Prettier. Збірка, `lint`, `typecheck` і `test` мають проходити перед
  кожним комітом. Повний набір перевірок: `npm run lint`, `npm run typecheck`, `npm run test`, `npm run build`.
- Доступність: підписи для кнопок-іконок, фокус з клавіатури, достатній контраст, не залежати лише від
  кольору. Мобільний екран першочерговий (ширина 360–430 px), далі планшет і десктоп.
- Продуктивність: початкове завантаження легке. Колоди з даними завантажуються окремими файлами за потреби.
- Залежності: тільки відомі, підтримувані пакети; записуй причину вибору в «Рішення». Не використовуй
  `npm audit fix --force`.
- Один осмислений коміт на завершений крок. Повідомлення комітів англійською.

## Дані та ліцензії

- Використовуй лише дані з офіційних джерел і лише після перевірки ліцензії. Кожне джерело, версію,
  дату завантаження та ліцензію запиши в `docs/DATA_SOURCES.md`. Сторінка «Джерела й ліцензії» в самому
  застосунку обов'язкова.
- Tatoeba: речення під CC BY (деякі CC0), потрібна атрибуція авторів. Умови комерційного використання
  не підтверджені, тому в `DATA_SOURCES.md` зазнач, що застосунок некомерційний (пет-проєкт), і внеси питання
  в «Черга рішень власника».
- Частотні списки та словники: перед використанням перевір ліцензію (зокрема CC BY-SA з вимогою зберігати
  ліцензію для похідних даних). Якщо умови неясні, не включай дані, а запиши питання.
- Переклади, які згенеровано ШІ, позначай у даних як неперевірені (`reviewed: false`) і не видавай за
  авторські. Якщо в етапі їх використано, скажи про це в `JOURNAL.md`.
- Не копіюй вміст чужих додатків (колоди Quizlet, Anki, Brainscape тощо) і не скрейпи сайти.
- Розмір: тримай стартові колоди невеликими; великі набори розбивай на частини.

## Безпека й заборони

- Працюй **лише всередині теки проєкту**. Не читай, не змінюй і не видаляй файли поза нею.
- Не роби `git push`, не створюй і не змінюй віддалені репозиторії, не деплой нікуди, не публікуй пакети.
  Локальні коміти дозволені.
- Не створюй акаунтів, не вводь паролів і ключів, не зберігай секретів у коді чи файлах. У застосунку
  немає трекерів, аналітики та запитів до сторонніх серверів під час роботи, крім завантаження власних
  статичних файлів.
- Нічого не встановлюй глобально (`npm install -g`, зміни PATH, системні налаштування). Лише залежності
  проєкту всередині його теки. Якщо Node.js чи npm відсутні, зупинись, опиши власнику, що потрібно
  встановити, і чекай.
- Завантаження файлів даних: лише з офіційних адрес, перелічених у `docs/DATA_SOURCES.md` після
  перевірки ліцензії; ніяких скриптів з невідомих джерел і виконання завантаженого коду.
- Не змінюй системні та безпекові налаштування. Не чіпай інші процеси.
- Якщо щось заборонене потрібне для завершення етапу, не роби цього: запиши в «Відомі проблеми» або
  «Черга рішень власника» й обійди іншим способом або пропусти.

## Середовище

Windows, PowerShell. Використовуй синтаксис PowerShell, шляхи з `\`, `npm` і `node`. Якщо команда не
спрацювала через PATH, не шукай обхід у системі: опиши причину в «Відомі проблеми» й запропонуй рішення
власнику.
