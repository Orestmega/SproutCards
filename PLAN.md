# План: застосунок із картками для вивчення мов (PWA)

Виконується Claude Code автономно, **трьома частинами**. Правила в `CLAUDE.md`, стан у `JOURNAL.md`.
Кожна частина містить кілька етапів, які виконуються підряд. Після частини Claude Code зупиняється.

| Частина | Етапи | Орієнтовна частка роботи |
|---|---|---|
| 1 | Етап 0 (підготовка), Етап 1 (ядро), Етап 2 (дизайн і колоди) | ~41% |
| 2 | Етап 3 (режими навчання), Етап 4 (готові колоди й джерела) | ~35% |
| 3 | Етап 5 (PWA і статистика), Етап 6 (документація й підготовка до публікації) | ~24% |

Частки це оцінка обсягу роботи, а не виміряна частка ліміту. Реальну вартість показує `/usage` до і після.

Правила виконання частини:
- Етапи всередині частини виконуються по порядку. Після кожного етапу: повний набір перевірок, окремий
  коміт, оновлення `JOURNAL.md` («Поточний стан» і запис етапу).
- Якщо ліміт закінчується посеред частини, Claude Code зупиняється на межі етапу (не посеред змін),
  оновлює `JOURNAL.md` і пише, з якого етапу продовжувати.
- Точка зупинки: після Етапу 3 застосунок уже корисний (картки, Learn, тест, озвучка на власних колодах).
  Якщо ліміти або час закінчуються, Етапи 4–6 можна відкласти без втрати цінності.

## Алгоритм навчання (специфікація для Етапів 1 і 3)

Рушій Learn, чисті функції, без залежності від UI:

1. Для кожної картки в сесії є **рівень** (0, 1, 2, 3...) і **напрямок** (A → B, B → A).
2. Рівень 0: показати слово мови, що вивчається, і варіанти перекладу (вибір відповіді).
3. Рівень 1: те саме слово, користувач вводить переклад.
4. Рівень 2: слово рідною мовою, користувач вводить слово мовою, що вивчається.
5. Правильно: рівень +1. Неправильно або «не знаю»: показати правильну відповідь, рівень −1 (не нижче 0),
   картка повертається в чергу через кілька карток (наприклад, через 3–5 позицій).
6. Картка «пройшла сесію», коли досягла останнього рівня й відповіла правильно. Тоді їй призначається
   дата наступного повторення за фіксованими інтервалами (1, 3, 7, 14, 30 днів). Після помилки інтервал
   скидається до першого. Інтервали й правила зберігаються в одному конфігураційному об'єкті.
7. Перевірка введеної відповіді: нормалізація (регістр, пробіли, діакритика за налаштуванням), кілька
   допустимих відповідей, дрібна друкарська помилка дає «Майже» з показом правильної відповіді (не
   зараховується як повністю правильна, правило вказати в коді).
8. Деталі розкладу повторення мають бути змінними: пізніше можна замінити фіксовані інтервали на SM-2
   або FSRS, не чіпаючи решти коду (інтерфейс `Scheduler`).

## Модель даних (орієнтир, остаточно в Етапі 1)

- `Deck`: id, назва, мова навчання, мова перекладу, опис, джерело, дата створення.
- `Card`: id, deckId, поля `term` і `translations[]`, мови, приклади речень, нотатки, прапор `reviewed`.
- `Progress` (на картку й напрямок): рівень, інтервал, дата наступного повторення, кількість помилок.
- `ReviewLog`: час, картка, режим, результат.
- `Settings`: мова інтерфейсу, озвучка, нових карток на день.
Усе зберігається в IndexedDB; експорт і імпорт у JSON.

## Етап 0. Підготовка

Завдання:
- Перевірити, що встановлено Node.js і npm (`node --version`, `npm --version`). Якщо ні, зупинитись і описати
  власнику, що поставити (цього не можна робити самостійно).
- Створити проєкт Vite + React + TypeScript (strict), налаштувати ESLint, Prettier, Vitest + Testing Library,
  скрипти `lint`, `typecheck`, `test`, `build`.
- Підключити PWA-плагін (маніфест, service worker), поки з тимчасовими іконками.
- Структура: `src/`, `public/`, `docs/`, `scripts/` (для підготовки даних).
- Документи: `README.md` (заглушка), `docs/DESIGN.md` (палітра й правила), `docs/ARCHITECTURE.md` (скелет),
  `docs/DATA_SOURCES.md` (порожня таблиця), `LICENSE` (MIT), `.gitignore`.
- `git init`, перший коміт. Каркас CI-конфігурації для GitHub Actions (без запуску).
- Заповнити «Середовище» і перші «Рішення» в `JOURNAL.md`.
Готовність: `lint`, `typecheck`, `test` (хоч один тест), `build` проходять; `npm run dev` запускається;
коміт зроблено; `JOURNAL.md` оновлено.

## Етап 1. Ядро: дані та алгоритм навчання

Завдання:
- Типи й модель даних, шар збереження (Dexie, схема з версіями, тести з `fake-indexeddb`).
- Інтерфейс `Scheduler` і реалізація з фіксованими інтервалами.
- Рушій Learn за специфікацією вище, нормалізація й перевірка відповідей, режим «Майже».
- Експорт та імпорт колод (JSON, перевірка схеми, повідомлення про помилки без втрати даних).
- Жорстке покриття тестами: послідовності відповідей, повернення помилок у чергу, зміна напрямку,
  дати повторення, крайні випадки (порожня колода, одна картка, дублікати).
Готовність: усі перевірки проходять, логіку можна використати без UI, `ARCHITECTURE.md` описує ядро.

## Етап 2. Оболонка застосунку, дизайн та колоди

Завдання:
- Дизайн-токени (світла тема з `docs/DESIGN.md`), базові компоненти (кнопка, картка-варіант, прогрес-смуга,
  бульбашка талісмана), маршрутизація.
- Талісман «Sprout» у SVG: кілька станів (звичайний, радий, підбадьорює).
- i18n `uk` та `en`, перемикач мови інтерфейсу, жодних хардкод-рядків.
- Екрани: головна (повторення на сьогодні, серія днів, колоди), список колод, колода з картками,
  створення та редагування колоди й карток, імпорт/експорт, налаштування.
Готовність: можна створити колоду, додати картки, перезапустити застосунок і побачити їх; перевірки
проходять; мобільна ширина 360–430 px виглядає охайно (перевір скріншотами через браузерні тести, якщо
доступно, або чесно запиши, що не перевірено).

## Етап 3. Режими навчання

Завдання:
- Картки з перевертанням (знаю / не знаю, інтеграція з Progress).
- Learn: екрани вибору й введення, відгук «Правильно / Майже / Неправильно», показ правильної відповіді,
  підсумок сесії, зворотний напрямок.
- Тест по колоді з оцінкою.
- Озвучка слів через `speechSynthesis`: вибір голосу за мовою; якщо голосу для мови немає, показати
  зрозуміле повідомлення, а не мовчати.
- Клавіатурне керування, доступність, анімації без надмірності.
Готовність: повний цикл «створити колоду → вчити → повторення на завтра» працює; тести логіки і
компонентів проходять; позначено, що озвучка й поведінка на iPhone не перевірені на пристрої.

## Етап 4. Контент: готові колоди та джерела

Завдання:
- Скрипти в `scripts/` для підготовки колод з відкритих даних (Tatoeba та частотні списки, після перевірки
  ліцензій і запису в `docs/DATA_SOURCES.md`). Скрипти відтворювані, виводять статичні JSON-файли.
- Стартові колоди EN ↔ UK: частотні слова з прикладами речень (для початку кілька сотень слів, розбиті
  на частини), плюс невелика тематична колода (наприклад, подорожі). Якщо якість перекладів не підтверджена
  джерелом, позначити `reviewed: false` і написати про це в `JOURNAL.md`.
- Каталог колод у застосунку: додати вбудовану колоду до своїх, завантаження частинами.
- Сторінка «Джерела й ліцензії» з атрибуцією.
Готовність: нову колоду можна додати з каталогу офлайн-доступною; атрибуція видна; ліцензійні питання,
що лишились, винесені в «Черга рішень власника».

## Етап 5. PWA, статистика, шліфування

Завдання:
- Повноцінні іконки та маніфест, офлайн-кеш (стратегія кешування описана в ARCHITECTURE), оновлення
  застосунку без втрати даних, пропозиція встановити на головний екран.
- Статистика: серія днів, кількість вивчених слів, прогрес колод (простими графіками без важких бібліотек).
- Нагадування в межах можливого для PWA (без серверних пушів; якщо недоступно, записати чесно).
- Доступність і продуктивність: пройти чек-лист, за можливості виміряти Lighthouse локально й записати
  реальні цифри.
- Обробка помилок і порожніх станів, захист від втрати даних (підтвердження небезпечних дій).
Готовність: застосунок працює офлайн у браузері після першого завантаження (перевірено в браузері, не на
пристрої); перевірки проходять; цифри Lighthouse або «не вимірювалось».

## Етап 6. Випуск: документація та підготовка до хостингу

Завдання:
- `README.md` (англійською): що це, як запустити, скріншоти, що перевірено, чого немає.
- `docs/ARCHITECTURE.md`, `docs/HOW_IT_WORKS.md` (українською, простими словами: як влаштовано, як працює
  алгоритм повторення, як зберігаються дані, як додати мову).
- `docs/IPHONE_TEST.md`: покрокова інструкція перевірки на iPhone (потрібна публічна HTTPS-адреса; варіанти
  безкоштовного статичного хостингу з плюсами й мінусами; нічого не деплоїти).
- Конфігурація для статичного хостингу (без деплою), фінальний повний прогін перевірок, чистка коду.
Готовність: власник може за інструкцією сам опублікувати сайт і поставити його на iPhone; всі перевірки
проходять; у `JOURNAL.md` список відомих проблем і «не перевірено на пристрої».

## Етап 7 (пізніше, лише за окремою командою власника). Акаунти та синхронізація

Не починати без явного запиту. Орієнтир: готовий хмарний сервіс, синхронізація локальних даних, конфлікти
вирішуються за правилами, описаними в ARCHITECTURE. Потребує рішень власника (сервіс, приватність, ціна).

вікні VS Code. Перед кожним запитом гляньте `/usage`, після частини прочитайте `JOURNAL.md` («Поточний
стан»). Між частинами можна почати нову розмову (`/clear`): стан зберігається у файлах.
